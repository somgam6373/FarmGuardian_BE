**Goal:** `POST /auth/login`, `GET /me`, `POST /me/onboarding`, `DELETE /me` in the shape of API spec §3, and `register_user` (the identity half of signup) as a tested building block. The `POST /auth/signup` route is a follow-up that needs the farm side's `create_field`.

**Architecture:** new bounded context `app/identity/` (pure `domain/password.py`, SQL repository, application service that commits, FastAPI router and schemas). Onboarding reads the user's zones through a new function of `farm/application/zone_reader.py`.

**Tech Stack:** Python 3.13, FastAPI, SQLAlchemy 2 `text()` SQL on psycopg 3, Pydantic v2, stdlib `hashlib.scrypt` (no new dependency), pytest against the PostGIS test database.

**Spec:** `docs/dev/2026-10-29-auth-design.md` (approved in chat 2026-10-29); frame = `docs/dev/팜가디언_API_명세.md` §3 (never edited).

## Global Constraints

- `팜가디언_API_명세.md` is the frame and **must not change**; `schema.sql` does not change either; no new dependency (`requirements*.txt` untouched).
- Responses: login 200 `{id, username}`; `GET /me` 200 `{id, username, onboarded}`; `POST /me/onboarding` 200 `{id, onboarded: true}`; `DELETE /me` 204 with an empty body. Errors in the common format: login failure 401 `UNAUTHORIZED` (one message for every cause); onboarding 422 `ONBOARDING_INCOMPLETE` with `details` `{zone_count: int, unconfirmed_zone_ids: [int]}` (ids ascending); body shape errors 422 `VALIDATION_ERROR`.
- Password: stored string `scrypt$<n>$<r>$<p>$<salt hex>$<hash hex>` with n = 2^14, r = 8, p = 1, a random 16-byte salt and a 32-byte hash (`dklen`), password UTF-8 encoded, comparison with `hmac.compare_digest`. `verify_password` accepts n a power of two in 2^4..2^16, r in 1..16, p in 1..4 and non-empty hex salt and hash; **anything else, and any parsing or scrypt error, is `False`, never an exception** (the dev user's `!` and the fixtures' `x` must not match). `scrypt` is called with `maxmem=256 MiB`.
- `register_user` uses `INSERT ... ON CONFLICT (username) DO NOTHING RETURNING id`, returns `None` when the name is taken, and **does not commit**.
- `login` runs exactly one `verify_password` also for an unknown username (against a fixed dummy hash), so timing does not reveal whether a name exists. Login fields are strings of 1..100 characters (422 beyond). Usernames are compared exactly (case-sensitive). `X-User-Id` is not used by login.
- `complete_onboarding`: already onboarded → return without any check and keep the first `onboarded_at`; otherwise no zone or any zone with `history_confirmed` false → 422 `ONBOARDING_INCOMPLETE`; otherwise `UPDATE users SET onboarded_at = now() WHERE id = :id AND onboarded_at IS NULL` and commit.
- `withdraw`: `DELETE FROM users WHERE id = :id`, commit (the foreign keys cascade); an already missing user is not an error at the service level (the route's `current_user` already answers 401 for a second call).
- Layers: `domain` imports nothing from the app; `presentation` calls only `application`; `identity` reads zones only through `farm.application.zone_reader`. `current_user` from `core/auth.py` protects `/me*`; `/auth/login` has no auth dependency.
- Code and identifiers in English, short Korean comments as in `app/core`; ruff line length 100 (Korean characters count double, wrap long strings); tests flat in `tests/`; commit messages in English; do not push; stage explicit paths only (the working tree has an unrelated uncommitted backlog xlsx and `.gitignore` change).

## Review Focus

- Every login failure answers with the identical 401 body, an unknown name still runs one verification, and a locked or malformed stored hash (`!`, `x`, empty, truncated, non-hex, absurd parameters) never raises. (Tasks 1, 2, 3)
- The stored hash never contains the password, salts differ, parameters are embedded and a hash made with other parameters still verifies. (Task 1)
- Onboarding is idempotent without re-checking, keeps the first timestamp, and reports `{zone_count, unconfirmed_zone_ids}` exactly; another user's zones never count. (Tasks 2, 3)
- Withdrawal removes the caller's user, fields, parcels, zones, spray records and judgments and touches nobody else's rows; the same header is then 401. (Tasks 2, 3)
- `register_user` rolls back with the caller's transaction and a taken name changes nothing. (Task 2)
