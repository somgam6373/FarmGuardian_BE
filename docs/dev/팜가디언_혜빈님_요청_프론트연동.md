## 1. 구역에 `harvest_at` 추가 — 결정됨

**왜.** 프론트는 구역마다 수확 예정일을 입력받는다 (밭 관리의 「수확 예정일」). 지도 시트에 「수확 D-N」을 보여주고, 판정 시기 체크에서 「수확 전 일수보다 여유가 며칠 남았는지」를 계산한다. 지금 API에는 이 값이 없다.

**요청.**
- `schema.sql`의 `zone`에 `harvest_at date` (NULL 허용) 추가.
- `ZoneOut`, `ZoneSummary`, `ZoneDetail` 응답에 `harvest_at: date | null`.
- `PATCH /zones/{id}` 본문에 `harvest_at?: date | null` (null로 비울 수 있음).
- `app/farm/application/zone_reader.py`의 `ZoneContext`에 `harvest_at`을 넣어 준다. 판정(`judgment`)이 이 값을 읽는다.

**규칙 (2026-11-02 승인, `2026-11-02-farm-harvest-address-plan.md` D1~D5).**
- `harvest_at`은 `planted_at`이 있으면 그 날짜 이후여야 한다 (같은 날은 허용). 어기면 422. 오늘보다 과거여도 막지 않는다 (판정에서 여유가 음수로 나올 뿐이다).
- `crop_id`가 바뀌면 `harvest_at`도 null로 돌린다 (`planted_at`과 같은 「새 작기」 처리).
- `planted_at`만 바뀌는 경우는 `harvest_at`을 그대로 둔다.

**완료 조건.** 위 응답·PATCH 테스트, 명세 `팜가디언_API_명세.md` §2·§5 갱신, `ZoneContext` 테스트.

**참고.** 판정 시기 체크가 이 값을 쓰는 규칙 변경(설계 문서 C1)은 **2026-11-02에 승인됐다.** 구역에 `harvest_at`이 없으면 ②는 지금과 같이 동작하므로 기존 구역·테스트는 영향이 없다. 혜빈이 이 항목을 못 하면 지도 시트의 D-N 표시와 ②의 여유 규칙을 함께 접는다 (설계 문서 C1의 fallback).

## 2. 구역 삭제 API — 결정됨: 만들지 않는다

**현상.** 프로토타입의 「밭 관리」는 구역이 2개 이상일 때 구역별 「구역 삭제」를 보여 준다. API에는 밭 삭제(`DELETE /fields/{id}`)만 있다.

**결정 (준혁, 2026-11-02).** `DELETE /zones/{id}`를 만들지 않는다. `팜가디언_PRD_수정_제안.md` §2 #5가 「구역 다시 나누기·삭제는 P1, 지금은 밭을 지우고 다시 만든다」고 정했고, 아키텍처 §7도 같다. 이 문서의 이전 판은 B안(API 추가)을 권장했으나 이 결정과 어긋나 고쳤다.

- 혜빈의 작업: 없음.
- 프론트: 「구역 삭제」 버튼을 없앤다. 잘못 나눴으면 밭을 지우고 다시 만든다 (기록·판정도 함께 지워지므로 확인 화면이 필요하다).
- 나중에 P0로 올리면: 남은 구역 도형을 그대로 둘지, 마지막 구역을 막을지(409 코드)를 그때 정한다.

## 3. 밭 주소 `address` — 서버 저장 (완료)

**현상.** 프론트의 밭에는 이름 외에 주소 문자열이 있다 (밭 목록과 밭 고르기에서 표시). `FieldOut`에는 주소가 없고, 지번(`lnm`)도 없다 (`lnm`은 `GET /parcels` 응답과 `field_parcel` 테이블에만 있다). 그래서 서버에 저장하지 않으면 주소를 되살릴 방법이 없다. 아키텍처 §8(브이월드 지오코더)의 「미정: 주소를 어느 응답에 넣을지」가 이 항목이다.

| 선택지 | 내용 |
|---|---|
| A. 프론트가 보관 | 밭 id → 주소를 브라우저에만 저장. 기기를 바꾸면 사라진다 |
| B. 서버에 저장 (**준혁 안**) | 아래 요청 |

**요청 (B).**
- `schema.sql`의 `field`에 `address text` (NULL 허용).
- `POST /fields` 본문에 `address?: string` (앞뒤 공백을 뺀 1~200자, 어기면 422). `FieldOut`에 `address: string | null`.
- `field_service.create_field(db, user_id, name, farmmap_ids, address=None)`처럼 주소를 받는 인자를 둔다.
- 값은 프론트가 주소 검색에서 고른 `jibun_addr`. 기존 밭은 null이다.
- 가입은 준혁이 맡는다: `POST /auth/signup` 본문에 `field_address?`를 받아 위 인자로 넘긴다 (설계 문서 B11). 혜빈이 이 항목을 받은 뒤에 준혁이 시작한다.
- 「읍·면」 같은 지역 구분은 프론트가 주소 문자열에서 뽑으므로 서버는 필요 없다.

**완료 조건.** `schema.sql`, 요청·응답 테스트 (공백만 있는 값·201자 → 422), 명세 §2·§5 갱신. 개발·테스트 DB에는 `ALTER TABLE field ADD COLUMN address text;`가 필요하다.

**안 받는 경우.** A로 간다. 준혁은 B11을 접는다.

## 4. 분할 방식: 격자 ↔ 띠 — 결정됨: A

**현상.** 프론트 「구역 나누기」는 가로·세로 경계 슬라이더로 **격자**를 만든다 (구역 최대 6개). 서버 분할은 한 방향 **띠**(`direction` + `ratios`, 최대 10개)다. PRD 수정 제안 #1이 「균등 분할 + 비율 분할(예 6:4)」을 P0로 정했고, 비율 입력이 경계 드래그를 대신한다.

| 선택지 | 내용 |
|---|---|
| A. 프론트가 띠에 맞춤 (권장) | 온보딩의 구역 나누기 단계를 「방향(`crosswise`/`lengthwise`) 고르기 + 비율 슬라이더」로 바꾸고, 미리보기는 `POST /fields/{id}/split-preview`를 쓴다. 서버 변경 없음 |
| B. 서버에 격자 추가 | 2차원 분할 도형 계산이 필요해서 크다 (선 긋기·드래그와 같은 P1 범위) |

참고: 미리보기는 서버가 계산하므로, 슬라이더를 움직일 때마다 호출하거나 놓았을 때만 호출하는 방식은 프론트가 정한다. 방향 이름은 밭의 긴 변 기준이라 화면 표현을 프론트와 정해야 한다 (아키텍처 §10-6). 이 항목은 **혜빈 쪽 코드 변경이 없는 안(A)이 기본**이다.

## 5. 작물 변경 시 기록 처리 — 결정됨 (서버 동작 유지)

**현상.** 프론트는 작물을 바꾸면 「이 구역의 살포 기록 N건도 함께 삭제돼요」라고 경고한다. 서버 `PATCH /zones/{id}`는 `crop_id`가 바뀌어도 기록을 지우지 않고 `planted_at`만 null로 돌린다 (새 작기).

**결정.** 서버 동작을 그대로 둔다. `팜가디언_PRD_수정_제안.md` §2 #6이 「작물을 바꾸면 새 작기로 보고 정식일을 새로 넣거나 비운다. 기존 기록은 지우지 않는다」고 정했다. 기록을 지우는 안은 `spraying` 컨텍스트를 건드리게 되어 경계도 넘는다. 혜빈의 작업은 없다.

- 프론트 문구를 서버에 맞춘다: 「기록은 남고, 심은 날과 누락 없음을 다시 확인해야 해요」. `planted_at`이 null로 바뀌면서 `history_confirmed`도 풀리기 때문에 (`zone_service.update_zone`) 「누락 없음」 안내까지 같이 해야 한다.
- 판정 ④(작용기작 연속 규칙)는 정식일과 무관하게 **구역의 전체 이력**을 본다 (판정 규칙 §4 ④ 「작기와 무관하다」). 작물을 바꾼 뒤에도 이전 작물에 쓴 약이 ④에 반영되는 것은 **의도한 동작**이다.

## 6. 심을 예정일 `plannedAt` — 결정됨: A

**현상.** 프론트에는 아직 안 심은 구역에 「심을 예정일」이 있다. 서버 `planted_at`은 오늘 이후 날짜를 받지 않는다 (422), 따라서 예정일을 저장할 곳이 없다.

| 선택지 | 내용 |
|---|---|
| A. 프론트가 제거 (권장) | 정식일이 없으면 「심기 전」으로만 표시한다. 서버 변경 없음 |
| B. `planned_at` 컬럼 추가 | 표시용 값이다. 판정에는 쓰지 않는다 |

## 7. 알아 둘 변경 (혜빈 코드 수정 없음)

- 준혁이 `spraying`에 **소프트 취소**를 넣는다. `spray_service.list_sprays()`의 기본값이 취소 기록을 **제외**하도록 두므로, `zone_service._last_spray`(`limit=1`로 호출)는 **코드를 고치지 않아도** 취소된 기록을 건너뛴다. `GET /fields`의 `last_spray`가 이렇게 동작해야 한다는 점만 알아 두면 된다.
- `PesticideBase`는 바꾸지 않는다 (`app/farm/presentation/schemas.py`의 `LastSpray`가 쓴다). 약제 정보 확장(회사·성분 등)은 새 모델 `PesticideDetail`에 넣어서 `GET /fields` 응답의 `last_spray`는 그대로다.
- 프론트가 새로 부르는 기존 API: 가입 화면에서 `GET /addresses/search` → `GET /parcels`(필지 여러 개 고르기, `matches_query`·`used_by_field_id`) → `POST /auth/signup`, 온보딩에서 `GET /me` → `split-preview` → `POST /fields/{id}/zones` → `PATCH /zones/{id}`의 `history_confirmed` → `POST /me/onboarding`. 요청·응답은 지금과 같다.
- 프론트는 온보딩 규칙(PRD 수정 제안 #9)대로 밭을 먼저 저장한 뒤 구역을 나눈다. 중간에 나가면 `GET /fields`에 **`zones: []`인 밭**이 정상 상태로 나온다 (재분할은 없으므로 이어서 나누거나 밭을 지운다). `FIELD_ALREADY_SPLIT`(409)은 지금과 같다.
- 프론트가 구역 이름 `maxLength`를 10에서 30으로 맞춘다 (서버는 30자). 「구역 삭제」 버튼은 프론트가 없앤다 (#2).

## 진행 방법 (제안)

1. 혜빈이 #1을 먼저 한다 (결정됨). #3은 받을지 답하고, #4·#6은 위 표의 선택지를 정해서 이 문서의 「상태」를 갱신한다.
2. 정해진 항목은 `schema.sql`·테스트·`팜가디언_API_명세.md`·Notion 명세를 같이 고친다.
3. 준혁은 `git diff origin/test -- app/farm`이 비어 있는지 확인하고, 프론트 쪽은 위 선택지(A)로 진행해도 되는지 그때그때 알려 준다.
