- 작성일: 2026-11-02
- 대상: 혜빈 (`app/farm`: 밭·구역·필지·분할)
- 배경: 프론트 프로토타입(`frontend/`)을 실제 API에 연결하다가 발견한 차이 중 **`app/farm` 안에서만 풀 수 있는 것**을 모았다. 나머지(판정·살포 기록·카탈로그·OCR)는 준혁이 `2026-11-02-frontend-integration-design.md`대로 처리한다.

## 1. 구역에 `harvest_at` 추가 — 결정됨

**왜.** 프론트는 구역마다 수확 예정일을 입력받는다 (밭 관리의 「수확 예정일」). 지도 시트에 「수확 D-N」을 보여주고, 판정 시기 체크에서 「수확 전 일수보다 여유가 며칠 남았는지」를 계산한다. 지금 API에는 이 값이 없다.

**요청.**
- `schema.sql`의 `zone`에 `harvest_at date` (NULL 허용) 추가.
- `ZoneOut`, `ZoneSummary`, `ZoneDetail` 응답에 `harvest_at: date | null`.
- `PATCH /zones/{id}` 본문에 `harvest_at?: date | null` (null로 비울 수 있음).
- `app/farm/application/zone_reader.py`의 `ZoneContext`에 `harvest_at`을 넣어 준다. 판정(`judgment`)이 이 값을 읽는다.

**제안 규칙 (확인 필요).**
- `harvest_at`은 `planted_at`이 있으면 그 날짜 이후여야 한다 (같은 날은 허용). 어기면 422. 오늘보다 과거여도 막지 않는다 (판정에서 여유가 음수로 나올 뿐이다).
- `crop_id`가 바뀌면 `harvest_at`도 null로 돌린다 (`planted_at`과 같은 「새 작기」 처리).
- `planted_at`만 바뀌는 경우는 `harvest_at`을 그대로 둔다.

**완료 조건.** 위 응답·PATCH 테스트, 명세 `팜가디언_API_명세.md` §2·§5 갱신, `ZoneContext` 테스트.

**참고.** 판정 시기 체크가 이 값을 쓰는 규칙 변경은 준혁이 따로 승인받는다 (설계 문서 C1). 승인이 안 돼도 **지도 시트의 D-N 표시 때문에 이 컬럼은 필요하다.**

## 2. 구역 삭제 API — 확인 필요

**현상.** 「밭 관리」에서 구역이 2개 이상일 때 구역별로 「구역 삭제」를 누른다 (삭제할 기록 수를 경고로 보여 준다). API에는 밭 삭제(`DELETE /fields/{id}`)만 있다.

| 선택지 | 내용 |
|---|---|
| A. 프론트가 맞춤 | 구역 삭제를 없앤다. 잘못 나눴으면 밭을 지우고 다시 만든다 (이 경우 기록도 함께 지워진다) |
| B. API 추가 (권장) | `DELETE /zones/{id}` → 204. 기록(`spray_log`)과 판정은 `ON DELETE CASCADE`로 이미 같이 지워진다 |

B로 한다면 정할 것:
- 남은 구역의 도형은 그대로 둔다 (지도에 빈 땅이 생김). 괜찮은가?
- 밭의 마지막 구역은 지우지 못하게 막을까? (프론트는 구역이 1개면 버튼을 숨긴다.) 막는다면 409 코드를 정해야 한다.

## 3. 밭 주소 `address` — 확인 필요

**현상.** 프론트의 밭에는 이름 외에 주소 문자열이 있다 (밭 목록과 밭 고르기에서 표시). `FieldOut`에는 주소가 없고, 필지 `lnm`(지번)만 있다.

| 선택지 | 내용 |
|---|---|
| A. 프론트가 보관 | 밭 id → 주소를 브라우저에만 저장. 기기를 바꾸면 사라진다 |
| B. 서버에 저장 (권장) | `field.address text` (NULL 허용), `POST /fields` 본문과 `FieldOut`에 `address`. 값은 프론트가 주소 검색에서 고른 `jibun_addr` |

B면 `POST /auth/signup`의 첫 밭 생성에도 같은 값이 필요하다. 그 부분(identity)은 준혁이 맡고, 혜빈은 `field_service`가 `address`를 받도록만 해 주면 된다. 「읍·면」 같은 지역 구분은 프론트가 주소 문자열에서 뽑으므로 서버는 필요 없다.

## 4. 분할 방식: 격자 ↔ 띠 — 확인 필요

**현상.** 프론트 「구역 나누기」는 가로·세로 경계 슬라이더로 **격자**를 만든다 (구역 최대 6개). 서버 분할은 한 방향 **띠**(`direction` + `ratios`, 최대 10개)다.

| 선택지 | 내용 |
|---|---|
| A. 프론트가 띠에 맞춤 (권장) | 3단계 화면을 「방향(가로/세로) 고르기 + 비율 슬라이더」로 바꾸고, 미리보기는 `POST /fields/{id}/split-preview`를 쓴다. 서버 변경 없음 |
| B. 서버에 격자 추가 | 2차원 분할 도형 계산이 필요해서 크다 |

참고: 미리보기는 서버가 계산하므로, 슬라이더를 움직일 때마다 호출하거나 놓았을 때만 호출하는 방식은 프론트가 정한다. 이 항목은 **혜빈 쪽 코드 변경이 없는 안(A)이 기본**이다.

## 5. 작물 변경 시 기록 처리 — 확인 필요

**현상.** 프론트는 작물을 바꾸면 「이 구역의 살포 기록 N건도 함께 삭제돼요」라고 경고한다. 서버 `PATCH /zones/{id}`는 `crop_id`가 바뀌어도 기록을 지우지 않고 `planted_at`만 null로 돌린다 (새 작기).

| 선택지 | 내용 |
|---|---|
| A. 프론트 문구를 서버에 맞춤 (권장) | 「기록은 남고, 심은 날을 다시 넣어야 해요」로 바꾼다. 서버 변경 없음 |
| B. 서버가 기록을 지움 | `spraying` 컨텍스트(`spray_log`)를 건드리게 되어 컨텍스트 경계를 넘는다 |

**확인 필요.** 판정 ④(작용기작 연속 규칙)는 정식일과 무관하게 **구역의 전체 이력**을 본다 (판정 규칙 §4 ④). 그래서 A로 가면 작물을 바꾼 뒤에도 이전 작물에 쓴 약이 ④에 반영된다. 의도한 동작인지 확인해 달라.

## 6. 심을 예정일 `plannedAt` — 확인 필요

**현상.** 프론트에는 아직 안 심은 구역에 「심을 예정일」이 있다. 서버 `planted_at`은 오늘 이후 날짜를 받지 않는다 (422), 따라서 예정일을 저장할 곳이 없다.

| 선택지 | 내용 |
|---|---|
| A. 프론트가 제거 (권장) | 정식일이 없으면 「심기 전」으로만 표시한다 |
| B. `planned_at` 컬럼 추가 | 표시용 값이다. 판정에는 쓰지 않는다 |

## 7. 알아 둘 변경 (혜빈 코드 수정 없음)

- 준혁이 `spraying`에 **소프트 취소**를 넣는다. `spray_service.list_sprays()`의 기본값이 취소 기록을 **제외**하도록 두므로, `zone_service._last_spray`(`limit=1`로 호출)는 **코드를 고치지 않아도** 취소된 기록을 건너뛴다. `GET /fields`의 `last_spray`가 이렇게 동작해야 한다는 점만 알아 두면 된다.
- `PesticideBase`는 바꾸지 않는다 (`app/farm/presentation/schemas.py`의 `LastSpray`가 쓴다). 약제 정보 확장(회사·성분 등)은 새 모델 `PesticideDetail`에 넣어서 `GET /fields` 응답은 그대로다.
- 프론트가 새로 부르는 기존 API: 가입 화면에서 `GET /addresses/search` → `GET /parcels` → `POST /auth/signup`, 구역 설정에서 `PATCH /zones/{id}`의 `history_confirmed`. 요청·응답은 지금과 같다.
- 프론트가 구역 이름 `maxLength`를 10에서 30으로 맞춘다 (서버는 30자).
